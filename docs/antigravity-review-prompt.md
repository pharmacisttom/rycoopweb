# Prompt สำหรับ Antigravity

คุณทำหน้าที่เป็น Senior Full-stack Engineer, QA และ Security Reviewer ของเว็บสหกรณ์ออมทรัพย์สาธารณสุขระยอง ให้ตรวจระบบทั้งหมดจาก repository และระบบ local ที่รันได้ แล้วประเมินส่วนที่ต้องพัฒนาเพิ่มเติม พร้อมจัดทำแผนพัฒนาต่อเป็นภาษาไทย

## วิธีทำงาน

- อ่าน AGENTS.md, docs/agents/issue-tracker.md, docs/agents/triage-labels.md, docs/agents/domain.md และเอกสารติดตั้งก่อนเริ่ม อ่าน CONTEXT.md/CONTEXT-MAP.md และ ADR ที่เกี่ยวข้องหากมี
- ตรวจสถานะ Git และ remote จริงก่อนระบุ branch หรือ commit ใช้หลักฐานจากโค้ด การทดสอบ และระบบที่รันได้ ห้ามสรุปว่าฟังก์ชันใช้งานได้เพียงเพราะ build ผ่าน
- รอบนี้ให้ตรวจและเสนอแผนก่อน ยังไม่แก้โค้ด ไม่เปลี่ยนรหัสผ่านสมาชิก ไม่แก้ข้อมูลจริง ไม่เดาเลขบัตรที่ถูกต้อง ไม่ deploy ไม่ push และไม่สร้าง GitHub Issues จนได้รับคำสั่งเพิ่มเติม
- ทดสอบการเขียนข้อมูลด้วยบัญชีและข้อมูลสมมติในฐานข้อมูลทดสอบเท่านั้น ถ้าไม่มีให้รายงานข้อจำกัดและทดสอบส่วนที่ไม่กระทบข้อมูลจริง
- อย่าแสดงเลขบัตรประชาชน รหัสผ่าน token หรือข้อมูลสมาชิกจริงในรายงาน screenshots และ logs ใช้ข้อมูลปกปิดหรือข้อมูลสมมติ

## สภาพระบบที่ต้องตรวจยืนยัน

- React/Vite frontend, PHP backend และ MySQL
- หน้าสมาชิก `/member/login` และ `/member/dividends` ใช้เลขบัตรประชาชนเป็น username บัญชีใหม่จากการนำเข้ามีรหัสผ่านเริ่มต้นร่วมกันตามข้อกำหนดเดิม ตรวจความเสี่ยงและเสนอวิธีเปิดใช้งานบัญชีที่เหมาะสม
- API `/api/member/dividends` ต้องใช้สมาชิกที่ผูกกับ PHP session และห้ามเห็นรายการของสมาชิกอื่น รวมทั้งกรณีดัดแปลง request หรือ localStorage
- ผู้ดูแลใช้ `/admin/dividends/import` และ API preview/confirm เพื่ออัปโหลด XLSX หรือ CSV UTF-8 มีแม่แบบที่ `public/templates/`
- ตาราง `member_dividends` อยู่ใน migration 013 ข้อมูล local มีปี 2567 จำนวน 2,429 รายการ และปี 2568 จำนวน 2,426 รายการ รวม 4,855 รายการ ครอบคลุม 2,508 สมาชิก ให้ตรวจยืนยันหากมีฐานข้อมูลให้เข้าถึง
- มี 4 รายการจากสองปีพักไว้เพราะเลขบัตรเดียวกันผูกกับสมาชิกสองคน อยู่ใน `storage/private/dividends-review.json` หากไฟล์มีอยู่ ห้ามรวมรายการหรือแก้ identity โดยไม่มีข้อมูลยืนยัน
- ไฟล์ private และฐานข้อมูล local ไม่ถูกส่งขึ้น GitHub ระบบอื่นอาจไม่มีข้อมูลเหล่านี้
- ระบบสมาชิกเดิมบางส่วนถูกปิดด้วย feature flags และมีโค้ดข้อมูลตัวอย่างอยู่ ต้องแยกข้อมูลจริง ข้อมูลสมมติ และฟีเจอร์ที่ยังไม่เปิดให้ชัดเจน

## ขอบเขตตรวจ

1. ตรวจหน้าเว็บสาธารณะ เมนู ข่าว เอกสาร รูปภาพ ติดต่อ แบบฟอร์ม เครื่องคำนวณ ลิงก์ และ error states รวมถึงมือถือ คีย์บอร์ด accessibility และการพิมพ์ PDF
2. ตรวจ authentication ทุก role, CSRF, session expiry/logout, rate limiting, 2FA, password changes, suspended accounts, ownership checks และสิทธิ์ API/backend โดยไม่พึ่ง frontend อย่างเดียว
3. ตรวจการเปิดเผย PII, localStorage, cache headers, logs, uploads, path traversal, XML/ZIP bomb, XXE, SQL injection, XSS และการป้องกันไฟล์ backend/private ภายใต้ Apache และ deployment จริง
4. ตรวจยอดปันผล รายรับ รายหัก ยอดสุทธิ การเลือกปี ความแม่นยำทศนิยม ปี พ.ศ. ข้อมูลว่าง สูตร Excel ที่ไม่คำนวณ เลขศูนย์นำหน้า คอลัมน์สลับ หัวตารางหาย และ duplicate identities
5. ตรวจ import preview/confirm ว่าไม่มี writes ใน preview, token ผูกกับ session/หมดอายุ, ยืนยันซ้ำ/พร้อมกัน, rollback, reimport ที่ไม่สร้างรายการซ้ำ, identity conflicts และการรักษารหัสผ่านเดิม ตรวจไฟล์แม่แบบจริงด้วย
6. ตรวจ schema/migrations, indexes, constraints, compatibility กับฐานข้อมูลเดิม, deployment, env/feature flags, backup/restore, monitoring และประสิทธิภาพสำหรับจำนวนสมาชิกจริง
7. รัน build และ tests ที่เกี่ยวข้อง ได้แก่ SecurityRegressionTest.php, DividendImportTest.php และ NavigationRedirectTest.mjs อ่านข้อกำหนดของ integration tests ก่อนรัน เพิ่มแผนทดสอบ E2E ที่ยังขาดโดยไม่แก้ระบบในรอบตรวจ
8. ตรวจส่วนหลังบ้านอื่นที่มีอยู่จริง เช่น role management, ข่าว/เอกสาร, LED, คำร้อง, สินเชื่อ และรายงาน แยกส่วนที่ทำงานจริงจาก placeholder และบริการภายนอกที่ตรวจไม่ได้

## สิ่งที่ต้องส่งมอบ

- ตารางสถานะฟังก์ชัน: ใช้งานได้ / พบปัญหา / ยังไม่ได้พัฒนา / ยังตรวจไม่ได้ พร้อมหลักฐานและผลกระทบ
- รายการปัญหาจัดลำดับ P0–P3 ระบุ path/line, ขั้นตอนทำให้เกิดปัญหา, expected/actual behavior, หลักฐาน, แนวทางแก้ และ acceptance criteria อย่ารายงานข้อสงสัยเป็นข้อบกพร่องที่ยืนยันแล้ว
- รายการข้อเสนอพัฒนาเพิ่มแยกจาก bugs ให้เหตุผลด้านสมาชิก เจ้าหน้าที่ ความปลอดภัย และการดูแลระบบ พร้อมความสำคัญและ effort โดยประมาณ
- แผนระยะสั้น 1–2 สัปดาห์ กลาง 1–2 เดือน และระยะถัดไป ระบุ dependency, owner role, deliverable, effort range, acceptance criteria, tests และความเสี่ยง ไม่กำหนดวันเสร็จแน่นอนหากยังไม่มีข้อมูลทีม
- สรุปเงื่อนไขที่ต้องผ่านก่อนเปิด production และ 5 งานแรกที่ควรเริ่ม พร้อมอธิบายเหตุผล
- รายการคำถามที่จำเป็นต่อเจ้าของระบบ และสิ่งที่ตรวจไม่ได้เพราะขาดสิทธิ์ ข้อมูล หรือ environment

เขียนรายงานให้ผู้อ่านที่ไม่เห็นประวัติแชทเข้าใจได้ ระบุ commit และ environment ที่ตรวจ ยึดผลตรวจจริง และแยกข้อเท็จจริง สมมติฐาน ข้อเสนอ และข้อจำกัดให้ชัดเจน
