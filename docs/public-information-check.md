## ข้อมูลที่ยังต้องให้เจ้าหน้าที่รับรอง

- เวลาเปิดทำการ, LINE/Facebook ทางการ และพิกัดแผนที่: ไม่พบหลักฐานจากหน้าที่ตรวจ จึงไม่แสดงค่าที่คาดเดาเป็นช่องทางทางการ
- ข้อมูลจริงในฐานข้อมูล VPS, สถิติการเงิน, อัตราปันผลย้อนหลัง และสวัสดิการ: ต้องเทียบงบ/มติ/ระเบียบที่รับรอง ไม่แก้ตัวเลขด้วยการคัดจากข้อมูลตัวอย่าง
- DatabaseSeeder ยังมี sample content ห้ามรันเพื่อแก้ฐานข้อมูลที่มีอยู่
- เว็บใหม่เคยตอบ 404 ที่ /api/public/home และ /api/public/coop-info ตามผลตรวจอ่านอย่างเดียวก่อนหน้า ต้องตรวจ config/response จริงบน TEST ก่อน deployment ไม่เปลี่ยน Nginx ในงานนี้

## ผลทดสอบและ rollback

`node tests/PublicContentReferenceTest.mjs` ตรวจค่าข้อมูลอ้างอิง ความตรงกันของ PHP config/React และ render หน้า Board, Officer, Contact, Footer, Deposits, Loans จริงโดยไม่ใช้ข้อมูลสมาชิกหรือเชื่อมฐานข้อมูล
รัน `npm run build`, PHP syntax เฉพาะไฟล์ที่เปลี่ยน และ `git diff --check` ก่อน commit; ผลจริงรายงานใน PR
ไม่ใช้ SSR render เป็นข้อพิสูจน์ว่า browser interaction หรือ MySQL integration ผ่าน
Rollback เป็นการ revert commit ของ PR แล้ว build ใหม่ ไม่ต้องย้อน schema/data เพราะไม่มีการแก้ฐานข้อมูลในงานนี้

## แผนหลังบ้านเพื่อแก้ข้อมูลภายหลัง

ปัญหาหลักคือ config PHP, mockData, ข้อความเขียนตายตัว และฐานข้อมูลมีข้อมูลคนละชุด
ควรต่อยอด controller/ตาราง CRUD เดิมให้เป็นแหล่งข้อมูลกลาง แทนสร้างระบบใหม่ทั้งหมด

| ลำดับ | ส่วนที่จะพัฒนา | ต่อจากระบบเดิม | เกณฑ์รับงาน |
| --- | --- | --- | --- |
| 1 | ข้อมูลสหกรณ์ | SettingController, config app, ตาราง settings ที่ต้องตรวจ schema ก่อนใช้ | แอดมินแก้ชื่อ/ที่อยู่/โทร/email/เวลา/ช่องทางที่ยืนยันแล้ว; Header/Footer/Contact/API ใช้ข้อมูลเผยแพร่ชุดเดียว ไม่ต้อง build |
| 2 | กรรมการและเจ้าหน้าที่ | BoardStaffController, boards/staff, MediaService | แก้ชื่อ/ตำแหน่ง/รูป/ลำดับ/วาระ คณะย่อย ที่ปรึกษา ผู้ตรวจสอบ; ปิดวาระเก่าโดยไม่ลบประวัติ |
| 3 | ดอกเบี้ยและผลิตภัณฑ์ | InterestRateController, DepositProductController, LoanProductController, ตารางเดิม | กำหนดวันเริ่ม/สิ้นสุด แนบประกาศ จำกัดวงเงิน/งวดตามสมาชิก; หน้าเว็บและเครื่องคำนวณอ่านอัตราที่มีผลชุดเดียว |
| 4 | ขั้นตอนเผยแพร่ | ใช้ workflow ข่าวเดิมเป็นต้นแบบหลังตรวจสิทธิ์ | ร่าง → ตรวจสอบ → เผยแพร่; แก้ร่างไม่เปลี่ยนหน้าจริงจนอนุมัติ; preview และ version conflict protection |
| 5 | สิทธิ์และประวัติ | RBAC/PermissionMiddleware/AccessService, AuditService | แยก view/update/publish ตามโมดูล แยกจากสิทธิ์บัญชีสมาชิก เก็บผู้แก้/เวลา/ก่อน–หลัง พร้อมคืนเวอร์ชันอย่างควบคุม |
| 6 | เปลี่ยนหน้าบ้านให้อ่าน API | api.js, หน้าแรก/ติดต่อ/บุคลากร/ดอกเบี้ย/แชตบอต | ไม่มีเลขการเงิน hardcoded ซ้ำ มี loading/error และวันที่มีผล; cache invalidation หลัง publish ไม่ใช้การ refresh ทั้งหน้ารัว ๆ |

เสนอเริ่มข้อ 1–2 ก่อน แล้วทำข้อ 3 พร้อมข้อ 4–5 เพราะอัตราดอกเบี้ยต้องมีการอนุมัติและหลักฐานย้อนหลัง
ตรวจ schema/permissions จริงและทำ migration แบบ additive เมื่อจำเป็น; แผนนี้ยังไม่ได้ implement, ไม่รัน migration หรือแก้ live data
